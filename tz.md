Версия: 1.1.
Дата исходного ТЗ: 18.10.2026.
Дата уточнений: 23.10.2026.
Версия JSON-формата остаётся 1: уточнения не изменяют поля файла.
Язык продукта: русский.

Документ описывает первую версию продукта и является основным источником требований для реализации. При расхождениях с более ранней концепцией применяется это ТЗ.

## 1. Назначение и принятые решения

Приложение помогает прорабу составлять планы нескольких строительных объектов, определять потребности в ресурсах, планировать расходы и печатать график работ. Финансист видит весь переданный план, помогает его заполнять и изучает планируемые траты по датам.

Первая версия:

HTML, CSS и обычный JavaScript без серверной части и регистрации.
Независимые копии данных на устройствах. Обмен JSON-файлами вручную.
Передача одного объекта либо всех объектов вместе, включая архив.
Иерархия: объект → этап → работа → ресурс → плановый платёж.
Дополнительные расходы можно создавать прямо у объекта, без этапа и работы.
Общая плановая стоимость и отдельно планируемые к оплате суммы по периодам.
Табличная финансовая сводка с раскрытием суммы до отдельных платежей.
Диаграмма Ганта: объекты, этапы, работы, даты, полосы длительности; масштабы — дни, недели, месяцы.
Архив объектов и этапов с восстановлением и окончательным удалением.
Работа на компьютерах и телефонах Android/iPhone.
Печать А3 и системная печать или сохранение в PDF.
Без процентов выполнения, задолженности, просрочек, поступлений и финансового согласования.

Технические решения, не определённые пользователем отдельно, зафиксированы далее как обязательные решения первой версии: правила округления, дата платежа по умолчанию, структура файлов, поведение при конфликтах и ограничения объёма. При реализации не заменять их дополнительными вопросами.

## 3. Запуск и техническая архитектура
### 3.1. Основной способ использования

Приложение открывается по HTTPS-ссылке на статический сайт. Статический хостинг раздаёт только файлы интерфейса и не хранит планы.

Пользователю не нужны установка инструментов, запуск локального сервера или настройка базы данных. Размещение готовых файлов на хостинге — задача поставки продукта, а не действие прораба или финансиста.

Автоматически публиковать сайт при разработке без отдельного поручения не нужно.

Основные браузеры:

Актуальный стабильный Chrome на компьютере.
Актуальный стабильный Chrome на Android.
Chrome и Safari на iPhone.

Интерфейс поддерживает ширину от 360 CSS-пикселей. На iPhone ограничения движка и системной печати учитывать отдельно.

### 3.2. Файлы и зависимости

Обязательные исходные файлы:

index.html.
styles.css.
app.js.

Разрешены дополнительные локальные JS-модули по ответственности, sw.js, manifest.webmanifest, локальные иконки, файлы тестов и README.md.

Финальный пользовательский интерфейс работает без сборки, npm, CDN и внешних API. Инструменты для тестирования могут иметь отдельные зависимости разработки с lock-файлом.

Использовать системные шрифты и локальные SVG или иконки. Не подключать аналитику, внешние шрифты, рекламу и телеметрию.

Пользовательские данные не отправляются по сети. Обмен файлами выполняет сам пользователь вне приложения.

### 3.3. Офлайн и установка

После первого успешного открытия по HTTPS и завершения кеширования интерфейс доступен без сети через service worker.

Включить manifest и поддержку установки на главный экран там, где это позволяет браузер. Это дополнительный способ открытия той же веб-страницы, а не отдельное нативное приложение. Установка не обязательна.

Показывать ненавязчивые состояния:

«Готово к работе без интернета».
«Есть обновление приложения».

Обновление активируется после закрытия форм или подтверждения пользователя, без потери введённых данных.

Кешировать только ресурсы приложения. Планы хранятся отдельно в IndexedDB.

Первая загрузка требует интернета. Не обещать вечное сохранение кеша или данных средствами браузера.

Открытие index.html через file:// не является обязательным поддерживаемым способом, особенно на iPhone. При таком открытии показать инструкцию использовать HTTPS-версию.

Локальный HTTP-сервер допустим для разработки. Приёмочные проверки выполняются через HTTPS либо localhost.

## 5. Модель данных и поля

Все сущности имеют:

Стабильный UUID.
Время создания.
Время изменения.

Время создания и изменения хранится в UTC ISO 8601. ID сохраняются при обмене файлами.

Плановые даты — строки YYYY-MM-DD без часового пояса. Отображение — ДД.ММ.ГГГГ.

Не преобразовывать календарные даты через UTC так, чтобы они сдвигались при смене часового пояса.

Поля календарных дат реализовать нативными input type="date" с доступными подписями. Значение хранить как YYYY-MM-DD; визуальный формат самого нативного поля зависит от языка браузера и ОС. В таблицах и подписях приложения использовать ДД.ММ.ГГГГ.
Открытие календаря не должно зависеть только от showPicker(): пользователь может нажать на само поле. Если нативный тип не поддерживается, использовать текстовое поле с явной подсказкой ДД.ММ.ГГГГ и строгой проверкой даты. Проверить выбор, очистку и отмену в формах на реальных Android и iPhone.

Строки обрезаются по краям.

Ограничения:

Названия — от 1 до 120 символов.
Комментарии — до 4000 символов.
Имя поставщика или исполнителя — до 200 символов.
Единица измерения — от 1 до 30 символов.
Подпись участника — до 80 символов.

Одинаковые названия допустимы: идентичность определяется ID.

Поля, не описанные ниже, не добавлять как обязательные.

| Название | Код |
| --- | --- |

Завершённая работа остаётся в плане до архивирования этапа или объекта либо удаления.

Статусы обеспечения:

| Название | Код |
| --- | --- |
| Не заказано | not_ordered |

Одна запись — одна потребность на конкретную дату. Несколько поставок или периодов аренды оформляются отдельными записями.

Категория не задаёт скрытых формул: стоимость всегда равна количеству, умноженному на цену.

Для аренды количество может быть числом смен или дней, а цена — ценой за смену или день. Автоматически умножать ещё и на длительность работы нельзя.

Справочник ресурсов с самостоятельным редактированием не нужен. Названия и единицы вводятся вручную; допустимы подсказки по уже использованным значениям.

Остатки материалов и списание не ведутся.

Статус обеспечения применим ко всем категориям, меняется вручную и не влияет на суммы.

### 5.5. Своя техника и инструмент

Флажок «Своё — без затрат» доступен только в категории «Техника и инструмент».

При включении показывать подтверждение, если есть ненулевые цена или платежи.

После подтверждения:

Цена становится нулевой.
Платежи удаляются.
Стоимость равна 0 ₽.
Количество сохраняется.
Дата потребности сохраняется.
Комментарий и статус обеспечения сохраняются.

В плане и Ганте соответствующая работа не исчезает.

У своего ресурса цена недоступна для редактирования, добавить платёж нельзя.

При снятии флажка пользователь вводит цену заново. Старые платежи не восстанавливаются.

Смена категории у своего ресурса требует сначала снять флажок.

При импорте ненулевые платежи или цена у своего ресурса считаются ошибкой, а не исправляются молча.

ГСМ, доставка, обслуживание и ремонт своей техники планируются отдельными платными ресурсами у той же работы либо общими расходами объекта. Пример: «Свой генератор» — 0 ₽ без платежей; «Топливо для генератора» — отдельный материал с ценой и платежом. Название или комментарий поясняет связь, специальное поле связи не требуется.
Если одновременно используется арендованная техника, аренду заводить отдельным платным ресурсом категории «Техника и инструмент». Не менять смысл флажка «Своё — без затрат» и не создавать скрытые расходы у нулевого ресурса.

### 5.6. Плановый платёж

Платёж принадлежит одному ресурсу или общему расходу.

Поля:

ID.
Название.
Сумма в целых рублях больше нуля.
Плановая дата.
Статус.
Фактическая дата при оплаченном статусе.
Необязательный комментарий.

Название по умолчанию — «Оплата». Допускаются, например, «Аванс», «Остаток».

Статусы:

| Название | Код |
| --- | --- |
| Запланирован | planned |
| Оплачен | paid |

Для paid фактическая дата обязательна, по умолчанию — сегодня.

При переводе обратно в planned фактическая дата очищается после подтверждения.

Промежуточной суммы фактической оплаты нет.

Оплаченный статус остаётся для простой отметки исполнения. Отдельные отчёты по фактическим расходам, задолженности, просрочкам и денежным остаткам не строятся.

Если planned имеет дату в прошлом, он остаётся обычным плановым платежом этого периода:

Не подсвечивается как просроченный.
Не переносится на сегодня.
Не вызывает напоминаний.
### 5.7. История изменений

Запись истории содержит:

UUID.

Для создания и удаления хранить необходимые значения для чтения истории, а не для автоматического восстановления.

Добавление или изменение ресурса и его автоматически созданного платежа — одно пользовательское действие с понятной сводкой.

Фиксировать:

Изменения полей.
Изменения статусов.
Изменения платежей.
Архивирование.
Восстановление.
Удаление дочерних записей.

Просмотр.
Поиск.
Фильтры.
Печать.
Экспорт.

История локальная, редактируемая вместе с файлом, не является юридическим аудитом.

## 6. Даты, сроки и статусы

Все длительности — календарные, включительно:

Работа с 01.11 по 03.11 длится 3 дня.
Суббота и воскресенье выделяются фоном на дневном масштабе Ганта.
Выходные не исключаются из срока.
Неделя — понедельник–воскресенье.

Нет календаря праздников и автоматических зависимостей.

Изменение даты одной работы не переносит другие работы, ресурсы и платежи.

До сохранения формы с изменёнными датами показать, что даты ресурсов и платежей останутся прежними.

Родительские сроки не пересчитываются автоматически.

Предупреждение показывается, если:

Этап выходит за границы объекта.
Работа выходит за границы этапа.
Дата потребности выходит за границы работы.

Сохранение разрешено после подтверждения.

Дата оплаты может быть раньше работы и потребности без предупреждения: предоплата — нормальный сценарий.

Новая работа наследует диапазон этапа, новый этап — диапазон объекта. Поля остаются редактируемыми.

Текущая дата используется только для начальных значений и линии «Сегодня», а не для изменения статусов.

## 7. Деньги и график планируемых трат
### 7.1. Числа и округление

Валюта — RUB.

Все денежные поля — в целых рублях без копеек.

Количество вводится с точкой или запятой, максимум два десятичных знака.

Внутреннее представление количества — целое число сотых единицы quantityHundredths.

Цена за единицу unitPriceRub — целое число.

Стоимость ресурса:

```text
costRub = floor(
  (quantityHundredths × unitPriceRub + 50) / 100
)
```

Это округление до ближайшего целого рубля. Ровно половина округляется вверх.

Считать через целочисленную арифметику. Промежуточное умножение выполнять через BigInt, а в JSON сохранять проверенные безопасные целые Number.

Не использовать последовательные вычисления через дробные float.

Отрицательные суммы запрещены.

Пределы одного поля:

Количество — до 1 000 000,00.
Цена — до 1 000 000 000 ₽.
Платёж — до 1 000 000 000 000 000 ₽.
Стоимость ресурса — до 1 000 000 000 000 000 ₽.

Любая агрегированная сумма должна оставаться не больше Number.MAX_SAFE_INTEGER.

Превышение отклоняется до сохранения или импорта с объяснением. Меньшие пределы вводить нельзя.

Эти пределы являются техническими ограничениями формата, а не рекомендуемыми бюджетами. Не показывать их в обычном интерфейсе до ошибки ввода. Сохранить проверку безопасного целого и переполнения агрегатов: снижение бизнес-лимита не заменяет точность расчёта.

Нулевые цена и стоимость допустимы, в том числе для своего оборудования. Нулевой платёж не создаётся.

Количество 0 не допускается.

Форматирование:

Разделитель тысяч — пробел: 125 000 ₽.
Количество без лишних нулей: 2, 2,5, 2,75.

НДС отдельно не считается: цена уже итоговая.

### 7.2. Автоматический платёж и разделение

При создании ресурса с положительной стоимостью автоматически создаётся один planned-платёж на полную стоимость.

Дата — дата потребности.

Пользователь видит это в форме и может выбрать другую дату до сохранения.

Один автоматический planned-платёж, который пользователь ещё не менял, обновляется при смене количества или цены до новой стоимости.

Отмечать его служебным полем autoManaged = true.

Изменение даты потребности само по себе не переносит даже автоматический платёж.

Любое ручное изменение платежа, его разбиение или отметка paid снимает autoManaged.

Изменение даты автоматического платежа прямо в первоначальной форме ресурса также снимает autoManaged.

При автоматическом пересчёте стоимости в ноль автоматический платёж удаляется. При последующем росте с нуля создаётся заново, если ручных платежей нет.

Смена статуса обеспечения на стоимость не влияет.

Для аванса и остатка пользователь редактирует список платежей:

Меняет существующий.
Добавляет второй.
Задаёт суммы и даты.

Форму ресурса вместе с платежами сохранять атомарно.

Удаление всех платежей при положительной стоимости разрешено только с явным предупреждением, что календарь трат пока не распределён.

Всегда показывать:

Стоимость ресурса.
Распределено по платежам.
Не распределено — если стоимость больше суммы платежей.
Платежи превышают стоимость на … — если сумма платежей больше стоимости.

В распределённую сумму включаются planned и paid.

Несоответствие разрешено как промежуточное состояние планирования, но:

Требует подтверждения при сохранении.
Остаётся видимым значком у ресурса.

Нельзя незаметно дополнять или уменьшать вручную настроенные платежи.

Если стоимость стала нулевой, ручные платежи удалить только с подтверждением. Без подтверждения изменение отменяется.

Простая частичная оплата:

Разделить 100 000 ₽ на платежи 30 000 ₽ и 70 000 ₽.
Первый отметить paid.

Частично оплаченного одного платежа нет.

### 7.3. Два основных показателя

Общая плановая стоимость — сумма стоимостей ресурсов и общих расходов выбранных активных объектов и этапов.

Она:

Не зависит от статуса работы.
Не зависит от статуса обеспечения.
Не зависит от отметки paid.
Не зависит от выбранного периода платежей.

Это общая стоимость плана, а не сумма оплат. Рядом подписать «За весь план».

Планируется к оплате — сумма только planned-платежей, чья плановая дата попадает в выбранный диапазон включительно.

Учитываются:

Выбранные объекты.
Категории.
Архивность.

Paid сюда не входят.

Прошедшие даты не исключаются, если входят в явно выбранный период.

Не добавлять стоимость ресурсов вторым слагаемым.

Не распределённая по платежам стоимость в этот показатель не попадает.

Фильтр категории применяется к обоим показателям. Диапазон дат — только к планируемым платежам.

При наличии нераспределённых или избыточных сумм показать ссылку «Проверить распределение платежей» на список соответствующих ресурсов.

Это проверка полноты плана, а не задолженность.

При несоответствиях сводка показывает число проблемных ресурсов и две отдельные суммы: «Не распределено» и «Платежи превышают стоимость». Не сворачивать их в одно сальдо. Список содержит путь к ресурсу, стоимость, сумму planned + paid и величину расхождения.
Перед любой выгрузкой объектов с расхождениями показывать это предупреждение и действия «Проверить распределение» / «Выгрузить как есть». Для резервного копирования и передачи незавершённого плана экспорт разрешён после явного выбора. Ошибки структуры и недопустимые значения по-прежнему запрещают экспорт.
Нераспределённая стоимость не добавляется в финансовую таблицу автоматически. Несоответствие сумм не превращает JSON в некорректный файл при импорте: после загрузки предупреждение сохраняется. Отдельного режима «отчёт финансисту» и статуса утверждения графика в первой версии нет.

## 9. Архив и удаление
### 9.1. Архив

Архив — раздел внутри локальной базы приложения, а не папка файловой системы.

Содержимое копится до явного удаления. Оно включается в выгрузку и резервные копии.

Архивировать можно:

Объект целиком.
Отдельный этап со всеми работами, ресурсами и платежами.

При архивировании объекта не менять собственные archivedAt этапов.

Восстановление объекта возвращает только те этапы, которые не были отдельно архивированы.

Архивирование не меняет статусы работ и платежей.

Архивные сущности и потомки архивного родителя по умолчанию исключены из:

Активного плана.
Общей плановой стоимости.
Календаря оплат.
Ганта.

В финансовом разделе и Ганте есть явное «Включить архив».

При включении учитывать каждую запись ровно один раз.

Архивный этап активного объекта не учитывается без этого переключателя.

Не превращать архивные planned-платежи в paid.

В разделе «Архив»:

Поиск по названию.
Переключатель «Объекты / Этапы».

Показывать:

Родительский объект.
Дату архивирования.
Даты плана.
Стоимость.

Разрешены:

Просмотр.
Детализация.
Выгрузка.
Печать.

Редактирование запрещено до восстановления.

Восстановление этапа внутри архивного объекта требует сначала восстановить объект. Это объясняется в интерфейсе.

### 9.2. Окончательное удаление

Объект и этап можно удалить навсегда из активного списка или архива.

Перед удалением:

Показать название.
Показать количество удаляемых дочерних записей.
Предложить «Скачать резервную копию».

Подтверждение:

Для объекта или этапа — вводом названия.
Для работы, ресурса или платежа — обычное явное подтверждение.

При наличии paid-платежей добавить отдельное предупреждение.

В случае отказа ничего не менять.

Удаление каскадное и атомарное:

Удаление платежа не удаляет ресурс.
Удаление ресурса удаляет его платежи.
Работа удаляется с ресурсами.
Этап — с работами.
Объект — со всем содержимым и его историей.

Общие расходы объекта не принадлежат этапам.

Отдельной корзины нет. Восстанавливать удалённое можно только из ранее сохранённого файла.

Архив — предпочтительное действие для законченного объекта или этапа, но не запрет удаления.

После окончательного удаления объекта хранить только служебную запись его ID и прежнего названия для предупреждения о повторном появлении при импорте.

Деталей затрат и истории в ней нет.

Если пользователь позже импортирует этот объект, явно спросить, восстановить ли его из файла.

## 10. Выгрузка и загрузка файлов
### 10.1. Два вида файла

«Скачать объект»:

Один выбранный объект полностью.
Его архивные этапы.
Ресурсы.
Платежи.
История.
Сведения о редакциях.

Доступно также для архивного объекта.

«Скачать все объекты»:

Полная резервная копия активных объектов.
Архивные объекты.
Служебные отметки об удалении объектов.

Локальные настройки устройства в неё не входят.

Формат:

Расширение .json.
Кодировка UTF-8.
MIME application/json.

Имена:

```text
plan-<безопасное-название>-YYYY-MM-DD-HHmm.json
plan-all-YYYY-MM-DD-HHmm.json
```

Недопустимые символы имени заменить дефисом.

Файл скачивается обычными средствами браузера.

На телефоне можно дополнительно использовать Web Share API для файла, если доступен. Всегда оставлять обычное скачивание.

Выгрузка отражает согласованный снимок из локальной базы, а не несохранённые формы.

При открытой изменённой форме сначала предложить сохранить или отменить ввод.

После запуска скачивания показывать:

Файл подготовлен. Проверьте, что он сохранён.

Браузер не позволяет гарантировать фактическую запись файла пользователем.

Отметка «Есть изменения после выгрузки» снимается для подготовленных редакций выбранных объектов, а не для всех объектов при выгрузке одного.

### 10.2. Структура формата 1

Верхний уровень JSON:

```json
{
  "format": "construction-resource-planner",
  "schemaVersion": 1,
  "exportId": "UUID",
  "exportKind": "object",
  "exportedAt": "2026-10-18T12:00:00.000Z",
  "exportedBy": {
    "name": "",
    "role": "foreman"
  },
  "currency": "RUB",
  "projects": [],
  "deletedProjectMarkers": []
}
```

exportKind:

object — строго один объект.
all — ноль или больше объектов.

Пример выше показывает только оболочку, а не готовый валидный файл object.

role:

foreman.
financier.
unspecified.

Все настройки округления фиксированы версией формата и не меняются значениями файла.

Каждый объект в projects содержит:

Поля объекта.
Вложенный массив stages, каждый элемент которого содержит свои works.
generalExpenses.
history.

Каждая работа содержит resources.

Ресурс или общий расход содержит payments.

Иерархия определяет принадлежность. Отдельные противоречащие родительские ID не хранить.

Для идентификатора использовать поле id.

Даты объекта, этапа и работы:

startDate.
endDate.

Даты потребности и платежа:

requiredDate.
plannedDate.
paidDate.

Служебные метки:

createdAt.
updatedAt.
archivedAt.
sortOrder.
revisionId.
ancestorRevisionIds.

Остальные основные поля:

Цена — unitPriceRub.
Количество — quantityHundredths.
Своя техника — isOwnEquipment.
Статус — status.
Категория — category.
Комментарий — comment.
Поставщик — supplier.
Название — name.
Единица — unit.
Сумма платежа — amountRub.
Автоматическое управление платежом — autoManaged.

При реализации документировать точную JSON Schema в file-format.schema.json, включая все поля и допустимые коды.

Неизвестные свойства отклонять с указанием пути.

Даты, диапазоны, уникальность ID и связи дополнительно проверять прикладным валидатором.

UUID не должны повторяться среди сущностей одного файла.

История не считается дополнительными живыми сущностями с теми же ID: ссылки в ней допустимы на удалённые записи.

### 10.3. Редакции объектов

Редакции ведутся на уровне объекта, а не всей базы. Иначе обмен одним объектом будет создавать ложные конфликты остальных.

При каждом сохранённом пользовательском действии, меняющем объект или его содержимое:

Генерировать новый revisionId.
Прошлый и все его предки сохранять в ancestorRevisionIds без повторов.

Архивирование тоже меняет редакцию.

Экспорт и импорт принятой редакции сами её не меняют.

Сравнение входящего и локального объекта с одинаковым ID:

| Ситуация | Поведение |
| --- | --- |
| Одинаковый revisionId и одинаковое содержимое | «Без изменений», пропустить |
| Одинаковый revisionId, но разное содержимое | Файл некорректен, запретить импорт этого файла целиком |
| Локальная редакция есть среди предков входящей | Входящая продолжает локальную |
| Входящая редакция есть среди предков локальной | Входящая устарела, по умолчанию не выбирать её для замены |
| Ни одна не предок другой | Независимые правки или неизвестная история; показать конфликт |

Сравнивать канонически, независимо от порядка ключей JSON, включая историю.

Игнорировать только метаданные оболочки файла.

При конфликте дать выбрать, какую целую версию сохранить. Автоматического слияния отдельных полей нет.

Если ни одна редакция не является предком другой, но есть общий ID среди множеств {revisionId + ancestorRevisionIds}, показать: «Вы оба изменили копии одного плана. Замена сохранит только выбранную версию; правки второй версии не объединятся».
Если общего предка нет, показать: «История этих версий не связана или неизвестна». Не утверждать, что параллельная работа доказана.
До выбора версии доступны отдельные скачивания локального объекта и входящего объекта. Входящий объект выгружается из проверенного снимка в корректной оболочке формата 1, без записи в базу и без изменения редакции. Имена файлов различают «локальная» и «входящая».
По умолчанию конфликтующий объект пропускается. Подтверждение замены прямо называет теряемую локальную версию и объясняет возможность вручную повторить нужные правки из сохранённой копии.
Сервер отсутствует, поэтому приложение не может узнать, что файл сейчас редактируют на другом устройстве, и не обещает межустройственную блокировку. Предупреждение выявляется только при импорте. В инструкции обмена указать: договориться, кто сейчас редактирует объект, и передавать актуальную копию по очереди.
Цепочка предков — список идентификаторов, а не дерево миграций базы. Сравнение редакций не требует экрана технического дерева; пользователю показываются понятные названия состояний.

Номер или время файла не доказывает актуальность.

Разрешить осознанную замену устаревшей или конфликтующей версии только после отдельного подтверждения и предложения резервной копии.

Совпадение названия при разных ID не является совпадением объектов. Добавить как отдельный, показав предупреждение об одинаковом названии.

### 10.4. Импорт отдельного объекта

Последовательность:

Пользователь выбирает JSON через стандартный выбор файла. На телефоне — системный файловый менеджер.
Файл полностью проверяется до любых изменений базы.
Показать объект, дату выгрузки, подпись, редакцию, архивность и сводку отличий.
Если локального ID нет — действие «Добавить объект».
Если ID есть — «Заменить этот объект» после сравнения редакций.
Предложить скачать локальную версию заменяемого объекта. Пропуск резервного скачивания разрешён явно.
После подтверждения заменить только выбранный объект целиком, включая архивные этапы, историю, ресурсы и платежи.
Другие объекты и настройки устройства не менять.
Сохранить в одной транзакции.
При ошибке или отмене оставить прежние данные.

Пример:

В базе есть «Сосны» и «Берег». Файл содержит ID объекта «Сосны».

После загрузки меняются только «Сосны», включая удалённые из входящей версии дочерние записи. «Берег» сохраняется без изменений по данным.

Если «Сосны» был архивным, входящая архивность явно показывается и после подтверждения принимается как часть версии.

### 10.5. Импорт всех объектов

По умолчанию режим:

«Добавить/обновить объекты из файла».

Объекты, которых нет в файле, сохраняются.

В списке для каждого входящего объекта выбрать:

«Добавить».
«Заменить».
«Пропустить».

Конфликты и устаревшие версии по умолчанию пропустить.

Несовместимые между объектами ID отклонить, включая совпадения с сущностями сохраняемых локальных объектов. Сначала проверить итоговый набор целиком.

Отсутствие объекта в файле или запись в deletedProjectMarkers не означает команду удалить его у получателя.

Отдельный режим:

«Восстановить полную копию».

Доступен только для exportKind = all.

Он целиком заменяет набор объектов и отметок об удалении, в том числе удаляет отсутствующие в файле.

Перед выполнением:

Показать количество добавлений, замен и удалений.
Предложить скачать всю текущую базу.
Требовать подтверждение фразой «ЗАМЕНИТЬ ВСЕ ДАННЫЕ».

Настройки устройства сохраняются.

Пустая полная копия допустима только с этим подтверждением.

Применять весь подтверждённый импорт атомарно, а не по одному объекту с частичным успехом.

Пока пользователь смотрит сравнение, изменение базы в другой вкладке делает сравнение устаревшим. Запретить применение и пересчитать его.

### 10.6. Сравнение изменений

Сравнивать по стабильным ID, а не текстовым названиям.

Показывать количества и раскрываемые списки:

Добавленных объектов, этапов, работ, ресурсов и платежей.
Удалённых объектов, этапов, работ, ресурсов и платежей.
Изменённых объектов, этапов, работ, ресурсов и платежей.

У изменённой записи:

Поле.
Прежнее значение.
Новое значение.

Обязательно сравнивать:

Сроки.
Количество.
Цену.
Стоимость.
Даты, суммы и статусы платежей.
Признак своего ресурса.
Статус обеспечения.
Архивирование.
Комментарии.

Для удалённых записей показывать прежний путь и сумму.

Перемещение работы между этапами — изменение привязки, а не удаление и создание.

Различия по вычисляемой стоимости показываются для удобства, но в файл стоимость не записывается как независимый источник истины.

При удалении родителя показывать число дочерних записей с раскрытием, без повторного сложения их стоимостей.

Общую стоимость до и после сравнивать по одинаковому составу архивности.

Сводка доступна:

Перед импортом.
Как «Результат последней загрузки» после успешного импорта на этом устройстве до следующего импорта.

Для новой базы — состав загружаемого плана без выдуманных изменений.

Не создавать систему согласования и отметки прочтения.

## 11. Сохранение на устройстве

IndexedDB — основной источник текущих данных.

Имена базы и хранилищ документировать в README.

Одна завершённая операция сохраняет данные и историю транзакционно.

Показывать:

«Сохранение…».
«Сохранено на устройстве».
«Не удалось сохранить».

При ошибке:

Не закрывать форму.
Не выдавать изменение за сохранённое.
Предоставить повторное сохранение.
Предоставить скачивание аварийной копии с явно указанным несохранённым вводом.

Обычный экспорт — только из согласованной базы.

Сохранять версию структуры локальной базы.

Миграции выполнять транзакционно, без автоматической очистки при ошибке.

При недоступности IndexedDB не показывать полноценный успешный рабочий режим:

Объяснить ограничение браузера.
Предложить повтор.
Предложить экспорт уже доступных в памяти данных.

Не предлагать отключать защиту браузера.

Для нескольких вкладок использовать номер поколения базы и проверку его внутри readwrite-транзакции.

Устаревшее сохранение отклонять с предложением обновить представление и сохранить ввод отдельно.

Между вкладками отправлять уведомления через BroadcastChannel при поддержке.

Не допускать незаметной перезаписи данных или импорта устаревшего сравнения.

Это защита вкладок одного устройства, а не синхронизация устройств.

Автосохранение не меняет ранее скачанный файл.

Индикатор последней выгрузки хранится отдельно по объектам и редакциям.

После очистки браузера, смены профиля или адреса сайта данные могут быть недоступны. Восстановление — из JSON.

Не обещать, что браузерные данные автоматически переносятся между телефоном и установленной PWA.

### 11.1. Напоминания о резервной копии и устойчивое хранение

Копия в IndexedDB, Cache Storage или другом хранилище того же сайта не считается независимой резервной копией: она может исчезнуть вместе с данными сайта. Не добавлять скрытое ежедневное скачивание и не полагаться на закрытие вкладки для сохранения или экспорта.
Различать очистку кеша файлов интерфейса и удаление данных сайта: очистка только кеша не обязательно удаляет IndexedDB; очистка данных сайта может удалить план.
В настройках показывать время последней подготовки полной выгрузки и состояние «Есть изменения после полной выгрузки». Факт физического сохранения файла не гарантируется.
Напоминание показывать, если в базе есть сохранённые пользовательские изменения после полной выгрузки и с предыдущей подготовки полной выгрузки прошло не менее 24 часов. Если полной выгрузки ещё не было, отсчитывать 24 часа с первого пользовательского изменения. Создание учебного примера не запускает отсчёт.
Проверять условие при запуске и после успешного сохранения. Напоминание — неблокирующая плашка «Скачайте резервную копию всех объектов» с кнопками «Скачать все объекты» и «Позже». «Позже» скрывает её на 24 часа на этом устройстве. Не вводить отдельные браузерные уведомления.
Выгрузка отдельного объекта не заменяет полную резервную копию и не сбрасывает это напоминание. Подготовка полной выгрузки сохраняет локально ID объектов и их редакций; новые изменения снова включают признак изменений. Метаданные не входят в JSON.
Если Storage API поддерживается, показывать в настройках статус persistent storage через navigator.storage.persisted() и кнопку «Запросить устойчивое хранение» через navigator.storage.persist(). Отказ или отсутствие API не блокирует работу и не вызывает повторных автоматических запросов.
Даже разрешённое устойчивое хранение не заменяет внешний JSON и не защищает от явного удаления данных пользователем. На экране не обещать абсолютную сохранность.

Полное восстановление удаляет отсутствующие объекты только после отдельного подтверждения. Режим добавления и обновления их сохраняет.

Вредоносные строки из названий и JSON отображаются как текст. Нет исполнения HTML или JavaScript и внешних запросов данных.
Перезапуск офлайн после первичной загрузки работает. Обновление приложения не теряет введённые данные. Закрытие и открытие браузера сохраняет локальный план в обычном режиме хранения.

### 18.5. Проверки уточнений версии 1.1

Проверить конфликт с общим предком, несвязанную историю, сохранение обеих копий до выбора и отсутствие изменений базы при отмене.
Проверить напоминание: 24 часа, отсутствие пользовательских правок, «Позже», экспорт одного объекта, полную выгрузку и последующую правку. Проверить отказ и отсутствие Storage API без блокировки приложения.
Проверить нативные даты и активные фильтры на мобильных устройствах. Оговорка о непроверенных реальных устройствах сохраняется.
Проверить отдельные ГСМ и свою технику: стоимость учитывается один раз; у своей техники платежей нет.
Проверить две отдельные суммы расхождений, предупреждение при экспорте и успешную резервную выгрузку с явным подтверждением. Обратная загрузка сохраняет предупреждения и все значения.
